
## Выбор метода и адреса эндпоинта

Рассматривались два варианта:

### Вариант 1: `PATCH /cards/:id` с телом `{"isDone": true}`
Универсальный PATCH для частичного обновления карточки. В будущем можно менять любые поля одним эндпоинтом.

**Почему отклонён:**
- Эндпоинт становится «божественным объектом»: принимает любые поля, валидация усложняется.
- Неясно по URL, что именно меняется — нужно читать тело запроса.
- Если завтра добавится поле `isUrgent`, придётся либо раздувать этот PATCH, либо заводить отдельный — и тогда два PATCH-а на один ресурс выглядят странно.

### Вариант 2: `PATCH /cards/:id/done` с телом `{"isDone": true}`
Отдельный эндпоинт, адресованный конкретному полю.

**Выбран этот вариант.** Обоснование:
- PATCH по смыслу = «частичное обновление», что точно соответствует задаче (меняем одно поле, а не всю карточку).
- Суффикс `/done` делает эндпоинт самодокументирующимся: по URL сразу видно, что происходит.
- В теле остаётся только `isDone: boolean` — валидация тривиальная, живёт в одном middleware.
- Если в будущем понадобится менять другие поля по отдельности (например, `isUrgent`), добавится отдельный эндпоинт `/cards/:id/urgent` — это чище, чем раздувать универсальный PATCH.

## Архитектурное решение

Новый эндпоинт ложится в существующие слои по тому же шаблону, что `DELETE /:id`:

- **Роут**: `cardsRouter.patch("/:id/done", validateToggleDone, cardsController.toggleDone)`
- **Middleware** `validateToggleDone`: проверяет, что `req.body.isDone` — boolean. При ошибке → 400. Контроллер об этой проверке не знает.
- **Контроллер** `toggleDone`: достаёт `id` из `req.params`, `isDone` из `req.body`, зовёт сервис, по результату выбирает 200 или 404.
- **Сервис** `toggleDone(id, isDone)`: ищет карточку, меняет поле, возвращает обновлённую карточку или `null`. Не знает про HTTP.

## Риски и как их избежать

1. **Ловушка порядка роутов.** Если добавить параметрический `/:id/done` выше точных путей, точные перестанут работать. В текущем роутере точных путей нет, но порядок фиксируем явно: параметрические — в конце файла.
2. **Дублирование валидации.** Проверка `isDone` должна жить только в middleware. В контроллере её быть не должно — иначе при изменении правил одну из копий забудут поправить.
3. **res в сервисе.** Если случайно передать `res` в сервис — граница слоёв сломана, задание не засчитывается. Сервис возвращает `Card | null`, контроллер сам решает про статус-код.
4. **Забытое `.ts` в импорте.** Самая частая ошибка темы — `Cannot find module`. Все импорты своих файлов — с расширением `.ts`.
